## 步骤 1：区分余额、订阅和 Key 限制

| 项目 | 作用 | 耗尽后的表现 |
| --- | --- | --- |
| 账户余额 | 余额分组产生的实际费用 | 余额不足时请求被拒绝 |
| 订阅额度 | 指定订阅分组和有效期内的用量预算 | 周期额度或订阅到期后不可继续使用该订阅 |
| Key 总额度 | 单个 Key 的累计消费上限 | 不影响其他 Key，但该 Key 被拒绝 |
| 5 小时/日/7 日限额 | 单个 Key 的滚动或周期预算 | 到窗口恢复前返回额度错误 |

余额和订阅是两套计费来源，不会自动互相兑换。Key 所属分组决定请求走余额模式还是订阅模式；不要假设订阅耗尽后一定自动扣余额。

## 步骤 2：理解倍率

用量记录中的 **原始费用** 是倍率前的模型费用，**实际费用** 是应用当前有效倍率后的扣费值。余额、订阅额度、Key 额度和限额使用实际费用累计。

有效倍率可能来自：

- 分组默认倍率；
- 管理员为当前用户设置的专属倍率；
- 生效时段内的峰值倍率；
- 图片等媒体请求的独立倍率。

因此不要只用一个分组数字反推所有请求。以模型广场、Key 页面和具体用量记录显示的倍率与实际费用为准。

## 步骤 3：核对一笔请求

完成最小请求后打开 **用量** 页面并刷新，逐项核对时间、Key、请求模型、上游模型、协议、输入/输出 Token、缓存 Token、倍率、原始费用、实际费用和状态。流式中断、工具调用或媒体请求的费用以最终用量记录为准。

## 步骤 4：识别额度错误

Key 额度耗尽通常返回 `429 API_KEY_QUOTA_EXHAUSTED` 或 OpenAI 风格 `insufficient_quota`；账户余额不足通常返回 `403 INSUFFICIENT_BALANCE`。普通限流也可能返回 `429`，需要结合错误码和 `Retry-After` 判断，不能只看状态码。

## 常见问题

### 订阅和余额应该选哪个？

订阅适合固定分组和周期预算；余额适合按实际使用扣费以及在多个余额分组间使用。购买前检查套餐有效期、周期额度、支持分组、并发和倍率。现有订阅与余额不会因为新购套餐自动合并。

### 能否定制企业套餐？

可以通过文章顶部 **联系客服** 提交预计模型、月用量、并发、协议和结算需求。是否提供、价格、额度和交付时间以管理员确认的方案为准，帮助文档不做固定承诺。

### 为什么没有退款按钮？

只有支付渠道同时启用退款和用户退款、订单状态满足条件时，订单页才显示申请入口。入口未显示时请通过 **联系客服** 提供订单号，不要重复创建支付订单。

### 提交退款后多久能到账？

退款需要经过订单校验、管理员处理和支付渠道确认，可能出现申请中、退款中、部分退款、已退款或退款失败。系统不承诺固定工作日；实际可退金额还受订单已退金额、当前可扣回余额、订阅权益和活动赠送影响。

## 计费口径

网关保存倍率前 `TotalCost` 和倍率后 `ActualCost`。余额、订阅和用户侧 Key 限额按 `ActualCost` 记录；上游账户配额可能使用独立账户倍率。用量争议必须以单条用量记录和请求 ID 核对，不能用上游账单总额直接除以请求数。

退款只对系统支持且当前支付实例允许的订单开放。用户申请不会直接修改订单或余额，而是进入退款处理状态；最终结果以订单状态和退款明细为准。
