## 步骤 1：记录完整现象

记录客户端版本、时间和时区、最终请求 URL、模型 ID、是否流式、HTTP 状态码、错误体和响应头 `X-Request-ID`。先删除 Key、Cookie 和对话隐私。

## 步骤 2：按状态码处理

| 状态 | 常见原因 | 先做什么 |
| --- | --- | --- |
| 400 | JSON 或参数不符合协议 | 用本文最小请求对比字段 |
| 401 | Key 无效、停用或过期 | 重新复制并检查 Key 状态 |
| 403 | 余额、分组、账户或 IP 限制 | 检查 Key 分组和账户状态 |
| 404 | Base URL、端点或模型错误 | 查看最终 URL 和 `/models` |
| 429 | Key 额度、速率或上游限流 | 读取错误 code，稍后退避重试 |
| 5xx | 本站或上游暂时故障 | 保留请求 ID，避免高频重试 |

## 步骤 3：最小化重现

关闭流式、工具和高级参数，只保留一个 user 消息。最小请求成功后逐项恢复设置，定位是哪一项触发问题。

## 协议错误结构

OpenAI 通常为 `{error:{type,message}}`；Anthropic 为 `{type:"error",error:{type,message}}`；Gemini 为 `{error:{code,message,status}}`。客户端应兼容缺失字段。对 `429` 和临时 `5xx` 使用带随机抖动的指数退避，但不要重试鉴权和参数错误。
