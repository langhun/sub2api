## 步骤 1：用当前 Key 获取模型

```bash
curl "<api_base_url>/models" \
  -H "Authorization: Bearer sk-demo-replace-me"
```

结果会按 Key 分组、平台和模型白名单过滤。同一账号的两个 Key 可能看到不同模型；后台或旧教程显示过的名称不代表当前 Key 可用。

## 步骤 2：区分模型 ID、显示名称和上游模型

- **请求模型 ID**：客户端实际发送的 `model`，必须与 `/models` 完全一致。
- **显示名称**：客户端或本站界面使用的标签，可以与请求 ID 不同。
- **上游模型**：模型映射后实际交给上游的 ID，可在管理员允许展示的用量字段中核对。

模型映射、别名和路由可能改变上游 ID，不能仅凭显示名称判断请求最终去了哪里。

## 步骤 3：确认协议能力

模型出现在 `/models` 中只说明该 Key 可以选择它，不保证所有端点和参数都可用。分别用最小请求验证：

| 能力 | 端点 |
| --- | --- |
| Responses | `/v1/responses` |
| Chat Completions | `/v1/chat/completions` |
| Messages | `/v1/messages` |
| Embeddings | `/v1/embeddings` |

图片、视频、语音、工具和推理档位还需要独立验证，不能从文本模型名称推断。

## 模型质量常见问题

### 同名模型一定来自同一种上游吗？

不一定。分组可能包含多个账号或路由，管理员也可能配置模型映射。模型 ID 是调用契约，不是某个固定账号、订阅等级或资源池的证明。

### 是否保证固定资源池或能力完全不变？

帮助文档不作此类无法由单次请求验证的承诺。本站能够核对的是请求模型、分组、映射、选中账号、用量记录和上游响应；具体可见信息取决于管理员权限和日志脱敏策略。

### 为什么同一模型表现不稳定？

提示词、上下文压缩、工具结果、推理档位、客户端版本、上游容量和路由账号都可能影响结果。先使用同一最小输入连续复现，并记录时间与 `X-Request-ID`，不要只用主观输出差异判断模型被替换。

## 模型发现边界

`/models` 是当前 Key 的动态能力入口，不是永久产品清单。模型可能因分组、白名单、上游状态或管理员配置变化而增加、隐藏或暂时不可用。客户端应允许刷新模型，并对已消失的 ID 给出明确错误。

模型质量调查至少需要：请求模型、上游模型（如有权限）、协议、客户端版本、推理参数、输入摘要、时间、状态码、耗时和 `X-Request-ID`。不要提交完整对话或 Key。
