# 充值赠送活动 PRD

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 状态 | 待确认，未进入开发 |
| 目标版本 | v1：全局单活动充值赠送 |
| 适用范围 | 用户余额充值订单，不含订阅、兑换码后台发放与管理员手工加款 |
| 业务归属 | DaiGua 自定义 Overlay 功能 |
| 上线前置 | 完成账务回归、退款回归、邀请返利口径回归和浏览器验收 |

## 2. 背景与目标

当前系统支持用户通过支付渠道购买余额，并可使用全局充值倍率。运营需要在不改变渠道实际收款金额的前提下，为符合条件的充值订单额外赠送余额，用于拉新、节日促销和短期转化活动。

本功能的目标是：

1. 管理员无需改代码即可开启、修改、暂停和定时结束一个全局赠送活动。
2. 用户在创建订单前能看到预计赠送和最终到账，但服务端订单快照为唯一可信结果。
3. 赠送不改变支付渠道收款、手续费、订单限额和原有充值倍率逻辑。
4. 每一笔赠送可审计、可统计、可追溯，且不把自定义业务逻辑写回上游业务层。
5. 退款、重复回调、邀请返利和并发创建订单均保持账务一致性。

## 3. 范围

### 3.1 v1 包含

- 单个全局活动，按百分比赠送。
- 最低充值金额、单笔最高赠送、开始和结束时间。
- 用户充值页实时预览。
- 管理后台配置和活动统计。
- 订单级赠送快照与管理端查询。
- 赠送不参与邀请返利。
- 对余额充值订单的退款保护与账务回归。

### 3.2 v1 不包含

- 优惠码、邀请码专属活动、首充、阶梯档位、会员等级差异化。
- 每用户限次、按自然日/月限额、裂变任务。
- 订阅购买赠送、管理员手工加款赠送、兑换码赠送。
- 多活动叠加、活动优先级、A/B 实验。
- 将赠送余额限制为特定模型、渠道或有效期的冻结余额。

这些需求存在时，以 v2 独立 PRD 扩展；不得在 v1 中以临时条件散落在支付代码中实现。

## 4. 术语与金额口径

| 名称 | 定义 |
| --- | --- |
| 充值金额 `paymentAmount` | 用户填写的余额充值面额，未包含支付渠道手续费。 |
| 实付金额 `payAmount` | 实际向渠道发起收款的金额，包含现有手续费和币种换算。 |
| 基础到账 `baseCredit` | 充值金额按系统既有充值倍率计算后的余额。 |
| 赠送金额 `bonusCredit` | 活动额外赠送的余额。 |
| 最终到账 `finalCredit` | `baseCredit + bonusCredit`，写入现有订单的 `amount`。 |
| 活动快照 | 在订单创建时固化的活动规则、基础到账和赠送结果；活动之后修改或关闭不会影响已创建订单。 |

金额全部采用两位小数，服务端以十进制金额库计算并在每一步按两位小数四舍五入，禁止使用前端浮点结果作为结算依据。

## 5. 核心规则

### 5.1 生效条件

一个余额充值订单仅在同时满足下列条件时享受赠送：

1. 活动总开关开启。
2. 订单类型为余额充值。
3. 服务端创建订单时处于活动开始时间（含）和结束时间（不含）之间；未填写某一时间表示该侧不限制。
4. 充值金额大于或等于最低充值金额。
5. 所有配置校验通过。

未满足任一条件时，赠送为 `0.00`，订单按原有充值流程创建。

### 5.2 计算公式

```text
baseCredit  = round2(paymentAmount x balanceRechargeMultiplier)
rawBonus    = round2(baseCredit x bonusRate / 100)
bonusCredit = maxBonus > 0 ? min(rawBonus, maxBonus) : rawBonus
finalCredit = round2(baseCredit + bonusCredit)
```

其中：

- `balanceRechargeMultiplier` 复用现有全局充值倍率。
- `bonusRate` 是百分比，例如 `20` 表示赠送基础到账的 20%。
- `maxBonus = 0` 表示不设单笔赠送上限。
- 赠送基数为基础到账，不是实付金额。这样在已有充值倍率的站点中，活动承诺与用户可见到账金额一致。

示例：充值 100，原有倍率 1.20，赠送比例 20%，单笔赠送上限 30：基础到账为 120.00，原始赠送为 24.00，最终到账为 144.00；支付渠道仍只收取原有手续费后的实付金额。

### 5.3 配置校验

| 配置 | 规则 | 默认值 |
| --- | --- | --- |
| 活动开关 | 布尔值 | 关闭 |
| 赠送比例 | 大于 0 且不超过 100 | 0 |
| 最低充值金额 | 大于或等于 0，保留两位小数 | 0 |
| 单笔最高赠送 | 大于或等于 0，保留两位小数 | 0（不封顶） |
| 开始时间 | RFC3339，统一以 UTC 保存和计算 | 空（立即可用） |
| 结束时间 | RFC3339，统一以 UTC 保存和计算 | 空（长期有效） |

当活动开启时，赠送比例必须有效；若开始和结束时间同时存在，开始时间必须早于结束时间。服务端拒绝非法配置，前端在提交前同步提示。

### 5.4 订单快照和活动修改

- 订单创建成功即写入不可变赠送快照；支付成功、超时、取消或失败均保留快照以便核账。
- 活动配置的修改只影响修改后新建订单，绝不回溯修改待支付或已支付订单。
- 订单支付回调晚于活动结束时间，仍按该订单创建时的快照到账。
- 同一订单无论回调多少次，只能入账一次，也只能产生一条赠送快照和一条完成审计记录。

## 6. 用户体验

### 6.1 充值页

当金额有效且活动符合条件时，在现有“到账余额”下方显示：

| 项目 | 展示示例 |
| --- | --- |
| 基础到账 | `$120.00` |
| 活动赠送 | `+$24.00` |
| 最终到账 | `$144.00` |
| 说明 | `活动赠送以创建订单时服务端计算结果为准。` |

以下情况不显示赠送行：活动关闭、未开始、已结束、金额未达门槛、输入金额无效或公共设置尚未加载完成。页面不得把“预计赠送”写成保证到账，也不得显示不存在的倒计时。

支付成功后的现有订单详情、通知邮件和余额流水应展示基础到账、赠送和最终到账的拆分；在 v1 前端页面无法完全呈现时，至少在订单详情和管理端审计中可查，不能只显示总额。

### 6.2 用户边界反馈

- 未达门槛时：`充值满 $X.XX 可享活动赠送。`
- 达到赠送上限时：`本单赠送已达活动上限 $X.XX。`
- 活动结束后：不提示错误，直接按普通充值显示。
- 服务端创建订单失败时：沿用现有支付错误反馈；不得先乐观展示或扣减任何余额。

### 6.3 管理后台

设置位置：现有后台“功能设置”通过 Custom Settings Panel 挂载“充值赠送活动”面板。

面板字段：活动开关、赠送比例、最低充值金额、单笔最高赠送、开始时间、结束时间，以及只读预览示例。保存前展示预计规则摘要，例如：`充值满 $10.00，按基础到账赠送 20%，单笔最高赠送 $30.00。`

单独的自定义管理页提供：

- 当前活动状态：未开始、进行中、已结束、已关闭、配置无效。
- 活动期间订单数、已支付订单数、赠送总额、实付总额、基础到账总额、最终到账总额。
- 按时间、用户、订单号、支付状态筛选的赠送明细。
- 单笔明细：订单号、用户、创建时间、支付状态、实付、基础到账、赠送、最终到账、规则快照和退款状态。

管理页只读统计不得影响支付链路；统计查询必须分页并使用索引。

## 7. 账务、退款与邀请返利

### 7.1 支付与入账

- `payment_orders.pay_amount` 始终保存实际向渠道收取的金额，不包含赠送。
- `payment_orders.amount` 保存最终到账余额，沿用现有兑换码入账、余额校验、支付完成通知和退款总额计算。
- 基础到账和赠送金额存入 Overlay 专属快照表，不能仅从后续配置反推。
- 订单写入后、向渠道发起支付前必须写入快照。快照写入失败时，订单立即标记为失败且不调用支付渠道；因此不会产生无快照的可支付订单。快照表以订单 ID 唯一约束去重，不产生孤立快照。

### 7.2 退款

用户发起退款时，沿用现有规则：其当前余额必须不少于该订单的最终到账金额。原因是赠送余额已经入账并可能被消费，不能在赠送已被用掉后仅退还实际支付金额。

全额退款时，渠道退款金额以实际实付金额为准；最终到账余额被扣回。部分退款如系统支持，必须按最终到账总额比例扣回余额和计算渠道退款，并在赠送快照中记录退款金额，不得重新按当前活动规则计算。

### 7.3 邀请返利

v1 默认规则：**赠送余额不参与邀请返利。** 邀请返利基数为 `baseCredit`，不是 `finalCredit`。这避免平台同时承担活动赠送和赠送部分返利的双重成本。

现有上游逻辑按 `payment_orders.amount` 作为返利基数，不能直接复用。实现时必须增加一个通用、可选的订单返利基数解析挂载：未启用 Overlay 时仍返回原有 `amount`；启用充值赠送 Overlay 且存在有效快照时返回 `baseCredit`。该挂载不得包含活动业务规则。

管理员可在 v2 增加“赠送参与返利”的开关；它必须是显式策略，不能通过修改倍率或订单金额间接实现。

## 8. 技术与模块化约束

### 8.1 目录与挂载边界

所有新增业务代码必须位于：

```text
backend/internal/custom/modules/recharge-promotions/
frontend/src/custom/modules/recharge-promotions/
backend/internal/custom/migrations/
```

上游目录只允许存在以下小型、稳定的挂载：

1. 支付服务的通用“余额到账调整”接口及注册方法。
2. 支付服务的通用“订单返利基数解析”接口及注册方法。
3. 充值页的通用预览扩展注册表渲染点。
4. Custom Runtime、Custom Settings Registry 和 Custom Registry 的一次性组合调用。

上游的 Handler、Service、Repository、Ent schema、全局支付配置、支付路由和既有页面不得承载充值赠送业务判断，不得批量移动或重构。移除该 Overlay 的注册后，上游支付应保持原有行为。

### 8.2 数据模型

新增 Overlay 追加式迁移，例如 `003_recharge_promotions.sql`，创建表 `custom_recharge_promotion_orders`：

| 字段 | 用途 |
| --- | --- |
| `id` | 主键。 |
| `payment_order_id` | 上游订单 ID，唯一索引。 |
| `user_id` | 用户 ID，便于后台筛选。 |
| `payment_amount` | 用户填写的充值金额。 |
| `pay_amount` | 订单实际实付金额快照。 |
| `base_credit` | 按现有倍率计算的基础到账。 |
| `bonus_credit` | 本单赠送金额。 |
| `final_credit` | 最终到账，应等于上游订单 `amount`。 |
| `bonus_rate` | 下单时的赠送比例。 |
| `min_amount` | 下单时的门槛快照。 |
| `max_bonus` | 下单时的上限快照。 |
| `campaign_started_at` / `campaign_ended_at` | 时间规则快照。 |
| `created_at` / `updated_at` | 审计时间。 |

约束：金额非负；`final_credit = base_credit + bonus_credit`；`payment_order_id` 唯一；为 `user_id, created_at` 和 `created_at` 建索引。迁移只追加到 Custom Migration Ledger，绝不修改上游 `schema_migrations` 或既有迁移文件。

### 8.3 接口契约

支付核心的通用到账调整接口只接收：订单类型、充值金额、基础到账、当前时间和用户 ID；只返回：额外到账金额与供订单创建后持久化的不可变结果。接口返回非法金额、负数、NaN、Infinity 或精度异常时，订单创建失败并记录错误，不得静默按零赠送继续。

前端仅通过公共设置读取活动预览所需字段；管理设置和订单统计接口使用现有认证与管理员权限。前端计算仅用于展示，所有订单计算、活动时间判定和封顶均在服务端再次执行。

## 9. 安全、风控与性能

1. 不信任客户端提交的赠送金额、活动状态或时间；创建订单只使用服务端配置和服务端 UTC 时间。
2. 创建订单时对配置做一次一致读取，并把结果固化；禁止支付回调时重新读当前活动配置。
3. 使用订单 ID 唯一约束和现有支付履约租约，保证重放回调和并发操作不会重复入账或重复返利。
4. 赠送计算不得引入外部网络调用、定时轮询或支付链路上的数据库全表扫描。
5. 后台统计走分页、时间范围和索引；大范围导出改为异步任务，v1 不提供全量导出。
6. 配置保存和活动明细查询记入现有管理员审计；不记录支付密钥、卡号、渠道签名或用户敏感信息。
7. 设置关闭只影响新订单；不删除历史快照，不对已创建订单反向扣款。

## 10. 指标与运营口径

| 指标 | 计算方式 | 用途 |
| --- | --- | --- |
| 参与订单数 | 有赠送快照且 `bonus_credit > 0` 的订单数 | 活动覆盖量 |
| 已支付参与订单数 | 上述订单中已完成的数量 | 实际转化 |
| 赠送总额 | 已完成订单 `bonus_credit` 求和 | 活动成本 |
| 实付总额 | 已完成订单 `pay_amount` 求和 | 收款规模 |
| 基础到账总额 | 已完成订单 `base_credit` 求和 | 原有负债 |
| 最终到账总额 | 已完成订单 `final_credit` 求和 | 总余额负债 |
| 赠送率 | 赠送总额 / 基础到账总额 | 成本强度 |
| 退款订单数 | 有赠送快照且产生退款的订单数 | 风险监控 |

统计按订单完成时间计算，默认使用站点时区展示、UTC 保存。取消、过期和失败订单不计入赠送成本，但在明细中保留。

## 11. 验收标准

### 11.1 功能验收

1. 活动关闭时，余额充值与当前生产行为完全一致。
2. 活动开启且满足条件时，创建订单的 `amount = baseCredit + bonusCredit`，`pay_amount` 未因赠送变化。
3. 最低金额、比例、封顶、开始时间和结束时间均按服务端规则生效。
4. 用户页面正确展示预计基础到账、赠送和最终到账；订单实际结果以服务端为准。
5. 活动修改、暂停或结束后，已有待支付订单仍按创建快照完成；新订单按新规则或无赠送创建。
6. 余额入账、邮件/订单记录、退款余额校验使用最终到账金额。
7. 邀请返利仅按基础到账金额计算，且无赠送订单仍保持上游原有返利结果。
8. 管理员能查看活动状态和分页明细，普通用户不能访问管理接口或其他用户明细。

### 11.2 一致性与回归验收

1. 重复支付回调、并发履约、履约中断后重试均只产生一次余额入账、一次赠送记录和一次邀请返利。
2. 创建订单与赠送快照写入任一步失败均整体回滚，无孤儿记录。
3. 配置非法、计算结果异常、数据库约束冲突均返回可识别错误，不生成可支付的错误订单。
4. 原有普通余额充值、订阅购买、兑换码、支付退款和邀请返利的现有自动化测试全部通过。
5. Custom Migration 在空库、已有生产迁移库和重复执行时均可通过，且不改写历史迁移校验和。
6. 前端 TypeScript、Lint、相关 Vitest、后端单测与集成测试、前后端生产构建全部通过。
7. 上线前在本地或预发布连接的隔离数据库完成真实事务和并发回归；生产只做已验证版本的最小发布和浏览器验收。

## 12. 发布与回滚

1. 合入前先完成 Overlay 模块单测、支付服务挂载回归、迁移回归和浏览器验收。
2. 首次发布代码时，活动默认关闭；迁移只创建空表，不改变任何历史订单金额。
3. 代码发布并验证健康检查、管理设置、普通充值页面和订单创建预览后，再由管理员开启活动。
4. 紧急止损只需关闭活动开关，新订单立即不再赠送；已创建订单按快照处理。
5. 如需代码回滚，保留 `custom_recharge_promotion_orders` 表和历史数据；后续版本应向前兼容读取，禁止删除或修改已执行迁移。

## 13. 上线前需确认的业务决策

1. 赠送比例上限是否固定为 100%，还是允许超过 100% 的特殊活动；本 PRD 建议 v1 固定不超过 100%。
2. 最低充值金额以用户填写的充值金额为准，还是以渠道实付金额为准；本 PRD 采用前者，用户更容易理解。
3. 活动页面是否需要公开宣传位；本 PRD 的 v1 只在充值页提示，避免承诺与配置失配。
4. 管理端统计是否需要按支付渠道和用户来源拆分；若需要，作为 v1.1 的只读筛选扩展，不改变赠送规则。
5. 是否接受“余额不足以覆盖最终到账额则不可退款”的现有规则；本 PRD 建议保持，避免赠送被消费后产生无担保退款。
