## 2. 背景与问题

Sub2API 是请求代理和调度框架。当前主要接入上游池模式：请求进入框架后，由现有账号、通道和分组调度链路选择上游目标。本项目不维护一套自有账号池，也不负责上游账号的注册、养号、额度补充或生命周期运营。

现有调度在部分路径上优先复用 sticky 绑定。一个历史上成功、但近期首字很慢的上游目标，可能持续承接同一会话请求，导致用户感知到较高的 Time To First Token（TTFT）。Issue #5262 关注慢目标持续粘滞；Issue #5916 关注池模式下是否应允许关闭持久化 sticky。

问题的本质不是“管理账号池”，而是框架需要一个可选的**请求路由策略**：在不破坏原有重试、会话和计费语义的前提下，利用近期观测到的首字延迟和错误质量，为候选上游目标排序，并在必要时绕过慢 sticky。

## 3. 产品定位

首字优先是一个挂载在 Sub2API 调度器上的 Overlay 策略模块：

```text
客户端请求
    -> Sub2API 核心鉴权/模型映射
    -> 核心调度器生成候选目标
    -> ttft-routing Overlay 评分与 sticky 决策
    -> 上游池中的某个目标
    -> 流式响应与指标采集
```

模块只决定“本次请求在已有候选目标中优先尝试谁，以及是否暂时绕过持久化 sticky”，不创建或维护上游账号池，不改变上游凭据，不绕过核心权限、额度、计费和审计。

## 4. 产品目标

### 4.1 核心目标

1. 在框架层提供可插拔的首字优先调度策略。
2. 降低请求的 TTFT，尤其是会话 sticky 到慢目标时的 TTFT P95/P99。
3. 保留上游池模式下既有的候选过滤、失败重试、限流、模型映射和计费语义。
4. 允许按全局、分组、模型和端点启用或关闭策略。
5. 使 pool mode 可以关闭持久化会话 sticky，同时保留请求内重试亲和。
6. 所有新增业务逻辑位于 Overlay；上游核心只增加最小、稳定、默认无行为变化的扩展钩子。

### 4.2 可量化目标（试运行阶段）

1. 在启用策略且存在有效候选的流量中，TTFT P95 相对基线降低至少 20%，或由项目负责人根据实测重新设定目标。
2. 首字前因策略触发的额外重选比例不高于 10%。
3. 请求成功率、完整流式完成率和上游错误率不得较基线恶化超过 1 个百分点。
4. 策略关闭后，调度选择、sticky 和重试行为恢复到启用前的核心路径。
5. 指标可按 `group_id`、模型、端点、目标标识和时间窗口查询，且不记录凭据或完整提示词。

## 5. 非目标

本期不做：

1. 自建、托管或自动补充上游账号池。
2. 上游账号注册、登录、养号、额度管理、封禁处置或密码更新。
3. 改写核心调度器的候选过滤、计费、限流、认证和失败分类规则。
4. 以 TTFT 指标替代健康检查、资格校验或安全策略。
5. 在首字已经返回后迁移流式连接到另一目标。
6. 默认改变所有用户的 sticky 语义；必须通过开关和灰度范围启用。
7. 引入独立微服务、消息队列或运行时插件系统。
8. 依赖供应商私有 API 获取不可验证的“排队位置”或账号质量。

## 6. 用户与使用场景

| 角色 | 需求 |
| --- | --- |
| 终端用户 | 同一模型请求更快看到首字，长会话不被偶发慢目标长期拖慢。 |
| 运营管理员 | 按分组、模型和端点控制策略，查看 TTFT、重选和失败影响。 |
| 框架开发者 | 在不污染上游业务路径的前提下替换或演进调度策略。 |
| 运维人员 | 能够快速关闭策略、定位目标质量、比较启用前后指标并回滚。 |

### 6.1 典型流程

1. 请求通过核心鉴权和模型映射，核心调度器生成符合资格的候选目标。
2. Overlay 读取请求上下文和短期内存指标，过滤没有足够样本的目标。
3. 若存在 sticky 目标且其近期 TTFT 或错误率明显恶化，策略返回“暂时绕过 sticky”。
4. 策略按综合分数选择候选目标；核心仍执行连接、重试和错误处理。
5. 收到首个有效上游 token 时记录 TTFT；请求结束时记录完成、错误和重试结果。
6. 管理员在观察窗口内比较基线与策略组数据，必要时关闭模块。

## 7. 术语与约束

| 术语 | 定义 |
| --- | --- |
| TTFT | 从向上游发出请求到收到第一个有效响应 token 的耗时。连接建立、HTTP 头和空事件不计为首字。 |
| 候选目标 | 核心调度器已判定有资格承接该请求的上游账号、通道或路由目标。具体粒度由核心提供。 |
| 持久化 sticky | 基于客户端会话标识，在多个请求间复用同一目标的绑定。 |
| 请求内重试亲和 | 同一请求发生失败重试时，优先沿用必要的会话/重试键，避免破坏上游上下文；不等于跨请求持久化 sticky。 |
| 慢目标 | 在相同作用域和时间窗口内，TTFT 或错误质量显著劣于候选基线的目标。 |
| 评分作用域 | 至少包括 `group_id`、规范化模型、端点类型；目标标识可作为更细粒度维度。 |
| 冷启动 | 样本不足以进行可信比较的目标或作用域。冷启动目标必须回退到核心默认策略。 |

硬约束：首字优先只能在核心已经给出的合格候选集合内工作；Overlay 不得自行扩大候选范围，也不得将无资格目标重新加入候选。

### 8.2 核心最小扩展点

核心只提供稳定的策略接口和一次装配调用，不承载首字优先业务规则。建议接口语义如下，具体命名以现有调度器风格为准：

```go
type RoutingPolicy interface {
    Select(ctx context.Context, in CandidateSelectionInput) (Decision, error)
}

type Decision struct {
    OrderedCandidateIDs []string
    BypassSticky        bool
    RetryAffinity       RetryAffinityMode
}
```

要求：

1. 没有 Overlay、模块关闭或策略返回错误时，核心使用原有顺序。
2. 核心继续负责资格过滤、并发占用、连接、重试、错误分类和释放资源。
3. 钩子只能改变候选顺序和 sticky 是否暂时绕过，不能直接操作账号状态。
4. 任何新增接口必须有 no-op 默认实现，避免上游同步或模块未注册时改变行为。
5. 若完全不增加该窄钩子，无法在不复制核心调度逻辑的情况下稳定实现全局首字优先；复制逻辑不作为本 PRD 方案。

## 9. 功能需求

### FR-01 模块开关

提供以下层级的开关，优先级从细到粗：端点/模型 > 分组 > 全局。

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `false` | 总开关，关闭后完全回退核心策略。 |
| `sticky_escape_enabled` | `false` | 是否允许在慢 sticky 时绕过持久化绑定。 |
| `pool_mode_sticky_policy` | `inherit` | `inherit`、`retry_only`、`keep`。 |
| `min_samples` | `20` | 作用域内目标进入评分前的最小样本数。 |
| `window_seconds` | `900` | TTFT/错误 EWMA 的观察窗口。 |
| `ttft_threshold_ms` | `15000` | 慢 sticky 的默认绝对阈值；需支持按作用域覆盖。 |
| `max_reselects_per_request` | `1` | 首字前最多因策略触发的重新选择次数。 |
| `cooldown_seconds` | `60` | 慢目标降权后的最短冷却时间。 |

配置必须有版本号、审计记录和回滚值；密码、token、cookie 等秘密不得进入配置或指标。

### FR-02 候选评分

Overlay 接收核心提供的候选列表，逐个计算可解释分数。建议使用归一化加权模型：

```text
score = w_ttft * normalized_ttft
      + w_error * error_rate
      + w_timeout * timeout_rate
      + w_load * load_penalty
      + w_cold * cold_start_penalty
      - w_weight * configured_priority
```

规则：

1. TTFT 使用作用域内的 EWMA，并保留 P50/P95 观测用于诊断。
2. 失败、超时和限流分别计数，不能只用成功请求计算质量。
3. 样本不足时使用作用域基线，不因偶然一次慢请求永久降权。
4. 目标被核心标记为不可用、无额度或无权限时，Overlay 不得将其排回候选。
5. 分数只用于同一请求候选的排序，不改变核心配置权重的含义；是否允许覆盖权重必须由独立开关控制，默认不覆盖。

### FR-03 Sticky 处理

1. `keep`：保持核心原有持久化 sticky 优先行为，只在候选顺序中进行有限优化。
2. `inherit`：沿用核心默认值，适用于渐进接入。
3. `retry_only`：不创建或使用跨请求持久化 sticky；同一请求内的失败重试保留必要的 retry affinity。
4. 当 sticky 目标满足以下任一条件时，可返回 `BypassSticky=true`：
   - 作用域内有效样本达到 `min_samples` 且 TTFT EWMA 高于阈值；
   - 近期连续失败或超时达到配置次数；
   - 核心已将目标标记为暂时不可用。
5. 绕过 sticky 只对当前请求生效，不删除已有绑定，不强制迁移后续会话。
6. 首字返回后不得重新选择目标。

### FR-04 Pool mode

`pool_mode=true` 表示 API Key 或 Bedrock 凭据使用池模式。该标识不等于“可以取消所有重试关联”。

本模块必须分别处理：

| 场景 | 行为 |
| --- | --- |
| 跨请求持久化 session sticky | `retry_only` 模式下不创建、不刷新、不读取作为首选。 |
| 原请求失败后的同请求重试 | 保留请求级 retry key 和必要的上游会话信息。 |
| 客户端显式提供 session ID | 不得因为有 session ID 就强制创建持久化池绑定。 |
| 非 pool mode | 默认保持核心 sticky 语义；只有显式开启 sticky escape 才绕过。 |

原有 `ensureOpenAIPoolModeSessionHash` 等逻辑若承担请求内重试职责，不得被简单删除；需通过适配层区分 durable sticky 与 retry-only。

### FR-05 指标采集

每个请求至少记录以下聚合维度：

```text
request_id（内部关联值）
group_id
normalized_model
endpoint_type
candidate_target_id（脱敏或内部 ID）
sticky_present
sticky_bypassed
selection_reason
attempt_count
ttft_ms
completed
error_class
```

指标要求：

1. 首字计时从实际向上游发出请求开始，到首个有效 token 到达结束。
2. 无首字的失败请求必须单独统计，不能丢弃或伪造 TTFT。
3. 流式中断、客户端取消和上游错误要区分。
4. 默认仅保留进程内聚合窗口；持久化明细需另行评审容量、隐私和索引。
5. 不记录完整 prompt、响应正文、授权头或上游凭据。

### FR-06 管理端配置与诊断

Overlay 管理页提供：

1. 全局和分组开关。
2. 模型/端点覆盖配置。
3. `retry_only`、sticky escape、最小样本、阈值、冷却时间和重选上限。
4. 目标质量表：样本量、TTFT P50/P95、错误率、超时率、最近更新时间。
5. 策略决策计数：正常 sticky、绕过 sticky、冷启动回退、策略错误回退。
6. 配置变更审计和“一键恢复上一版本”。

前端只负责展示和提交配置，后端必须再次校验权限、范围和数值上下限。模块关闭时，页面可显示历史诊断数据，但不能继续触发策略。

建议接口（路径可按现有 custom 路由约定调整）：

```text
GET  /api/v1/custom/ttft-routing/config
PUT  /api/v1/custom/ttft-routing/config
GET  /api/v1/custom/ttft-routing/metrics
POST /api/v1/custom/ttft-routing/rollback
```

## 10. 数据与一致性设计

首期不新增独立账号池表。配置和审计使用 Overlay 自有命名空间，建议：

```text
custom_ttft_routing_settings
custom_ttft_routing_audit_logs
```

约束：

1. 设置以 `scope_type + scope_key + setting_key` 唯一定位。
2. 迁移只新增 Overlay 表和索引，不修改上游账号、会话、计费表结构。
3. 进程内 EWMA 在重启后允许冷启动；不得把单进程瞬时状态误当成永久账号质量。
4. 多实例部署时，首期每实例独立统计并在管理页明确显示；跨实例共享指标作为后续能力，不阻塞首期。
5. 配置读取失败时使用安全默认值：模块关闭、核心原有调度。

## 11. 安全、权限与隐私

1. 只有管理员或具备调度策略权限的角色可读写配置和诊断数据。
2. 目标标识使用内部 ID 或稳定脱敏值，禁止暴露上游 token、邮箱、cookie 和完整 URL 查询参数。
3. 设置变更写入审计日志，记录操作者、范围、旧值、新值和时间。
4. 策略不得通过绕过核心资格检查来访问被禁用、过期或无权限目标。
5. 指标查询必须限制时间窗口、分页和聚合粒度，避免高基数查询拖垮服务。

## 12. 兼容性与故障回退

### 12.1 默认兼容

以下条件任一成立时，行为必须等同核心默认调度：

- 模块未注册；
- 全局或作用域开关关闭；
- 配置解析失败；
- 指标样本不足；
- Overlay 评分超时或返回错误；
- 候选列表为空或核心拒绝 Overlay 决策。

### 12.2 故障回退顺序

```text
Overlay 决策失败
    -> 丢弃本次 Overlay Decision
    -> 使用核心原始候选顺序和 sticky 决策
    -> 继续核心既有重试/错误处理
```

不得因为指标采集失败阻断用户请求；指标链路必须是 best effort。

## 13. 观测与验收指标

### 13.1 业务指标

| 指标 | 口径 | 验收方向 |
| --- | --- | --- |
| TTFT P50/P95/P99 | 首字成功请求的毫秒数 | P95/P99 下降，P50 不显著恶化 |
| 首字成功率 | 收到首字的请求数 / 总请求数 | 不低于基线 |
| 完整完成率 | 正常完成流式请求 / 总请求数 | 不低于基线 |
| 重选率 | 策略触发重选请求 / 总请求数 | 受上限约束 |
| Sticky 绕过率 | 绕过 sticky 请求 / 有 sticky 请求 | 可解释、可按作用域分析 |
| 上游错误率 | 按错误分类统计 | 不出现系统性上升 |

### 13.2 技术指标

1. Overlay 决策耗时 P99 小于 5 ms（不包含上游网络请求）。
2. 指标采集不得阻塞首字转发线程。
3. 配置缓存读取失败时 100% 回退关闭策略。
4. 管理诊断接口不能返回秘密字段。

## 14. 测试计划

### 14.1 后端单元测试

覆盖：

1. EWMA、样本窗口、阈值和冷启动计算。
2. TTFT、错误率、超时率的综合排序。
3. sticky 正常、sticky 绕过和冷启动回退。
4. `retry_only` 不产生跨请求 durable sticky，但保留同请求重试亲和。
5. 候选为空、核心已过滤目标、配置非法和策略异常。
6. 并发读写指标窗口的竞态检测。

### 14.2 集成测试

1. 核心调度器未注册 Overlay 时行为快照不变。
2. 模块开关从开到关后立即回退核心策略。
3. pool mode 携带显式 session ID 时不创建持久化绑定。
4. 上游首字前失败时按核心规则重试，首字后不换目标。
5. 配置、审计和权限接口的成功与拒绝路径。

### 14.3 前端测试

1. 管理页开关、范围覆盖和数值校验。
2. 指标表加载、空状态、错误状态和分页。
3. 无权限用户不能编辑配置。
4. 模块关闭时页面不发送策略写入请求。

### 14.4 发布前验证

## 15. 灰度与发布计划

### Phase 0：观测准备

只采集 TTFT 和错误质量，不改变候选顺序。验证指标定义、采样量、隐私脱敏和管理诊断。

### Phase 1：影子评分

计算候选排序并记录“如果启用将选择谁”，但实际仍使用核心顺序。比较离线命中率和决策开销。

### Phase 2：小范围启用

仅对一个低风险分组或模型开启 `enabled=true`，保留 `sticky_escape_enabled=false`，观察至少一个完整业务高峰窗口。

### Phase 3：启用 sticky escape

在指标稳定后，对明确存在慢 sticky 的作用域开启 sticky escape；每次只调整一个作用域，保留审计和回滚值。

### Phase 4：pool mode retry-only

对确认兼容的池模式分组启用 `retry_only`，重点观察会话连续性、失败重试成功率和上游限流变化。

任何阶段出现完成率下降、错误率持续升高、策略决策异常或核心资源占用异常，应立即关闭作用域开关，而不是直接修改上游账号状态。

## 16. 回滚方案

1. 管理端将作用域或全局 `enabled` 设为 `false`。
2. 核心 no-op/回退路径立即接管后续请求。
3. 不删除 sticky 数据，不修改上游账号和凭据。
4. 若接口或迁移出现问题，按 Overlay 发布流程回滚应用版本；新增表可保留但不得被核心路径强依赖。
5. 回滚后继续保留只读指标，便于判断是策略、上游质量还是核心路径问题。

## 17. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| TTFT 样本受模型、提示词或时段影响 | 误判目标质量 | 按分组/模型/端点分作用域，设置最小样本和 EWMA。 |
| 频繁绕过 sticky | 上游会话缓存命中下降 | 单请求重选上限、冷却时间和灰度开关。 |
| pool mode 误删重试关联 | 重试失败或上下文丢失 | 明确 durable sticky 与 retry-only 两条链路并测试。 |
| 进程内指标重启丢失 | 冷启动阶段排序不稳定 | 冷启动回退核心策略，管理页显示样本状态。 |
| 核心扩展点过宽 | 上游同步冲突和维护成本增加 | 只允许改变候选顺序与 sticky bypass，业务规则全在 Overlay。 |
| 诊断高基数拖垮服务 | 管理接口和运行时抖动 | 聚合窗口、分页、时间范围限制和 best-effort 采集。 |

## 18. 验收标准

满足以下条件才可宣称首期完成：

1. `ttft-routing` 后端和前端代码全部位于 `custom` Overlay，只有固定挂载点存在最小适配代码。
2. 模块关闭、配置错误、样本不足和策略异常时，核心调度行为保持不变。
3. 候选评分、慢 sticky 绕过、冷启动和请求内重试亲和均有回归测试。
4. pool mode 的 `retry_only` 行为通过显式 session ID 和失败重试测试。
5. 管理端具备配置、指标、权限、审计和回滚能力。
6. 独立端口 A-B 测试证明 TTFT 改善达到项目设定目标，且成功率、完成率和错误率没有超出允许回归范围。
7. 上游同步边界检查通过，没有新增散落在上游业务文件中的首字优先规则。
8. 发布记录包含配置默认值、迁移说明、验证命令和回滚步骤。

## 19. 待确认事项

1. 核心候选目标的实际粒度是账号、通道还是账号-模型组合。
2. 生产环境是否多实例；若是，首期是否接受实例级指标而非全局聚合。
3. 上游 session 缓存对跨目标切换的容忍度，以及哪些端点必须强制保持 sticky。
4. TTFT 阈值是否统一使用 15 秒，还是按模型/端点建立基线阈值。
5. 管理员角色中是否已有独立的“调度策略配置”权限。
6. 核心调度器采用何种最小钩子形态，以便不扩大上游同步冲突面。
