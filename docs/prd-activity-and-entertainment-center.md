## 2. 背景与问题

站点需要一次性补齐排行榜、普通签到、运气签到、签到盲盒、余额转账、红包和娱乐大厅，并提供完整后台治理能力。当前分支已完成核心用户链路与统一设置第一阶段：各模块均有真实服务、数据表和用户界面。资金治理、可靠投递、旧数据验收报告、娱乐风控和管理端运维闭环仍需按本文上线门槛继续收敛。

本项目不是“把页面放出来”，而是建立从入口、路由、API、服务、事务、数据库、审计、定时任务到后台配置的完整链路。既有签到及娱乐钱包数据必须无损迁移，任何涉及余额的操作必须可对账、可重试、不可重复入账。

## 3. 产品目标

1. 用户可在统一的“娱乐与活动”入口完成签到、盲盒、转账、红包、排行榜和娱乐游戏操作。
2. 管理员可在同一个“功能开关”页面完成入口、访问、业务规则、奖池和口令格式配置，不再分散维护。
3. 所有余额变化具备不可变账务流水、业务来源、幂等键和前后余额，可完成审计与资金守恒核对。
4. 旧 `checkin_records`、既有签到设置、旧娱乐钱包/奖池数据可验证、幂等地迁移，不丢历史、不重复发钱。
5. UI 延续本站现有布局、组件、浅色/深色和中英文体系，参考外站功能但不复制其页面。

## 4. 非目标

- 不在首期提供用户间借贷、礼物交易、提现或法币兑换。
- 不把排行榜结果作为真实财富证明。
- 不允许管理员直接修改历史账务流水；纠错必须产生反向或补偿流水。
- 不在未完成公平性、合规和地区限制评估前开放高风险博彩式玩法。
- 不直接复制来源不明或许可证不兼容的上游素材、文案和视觉资源。

## 5. 用户与权限

| 角色 | 权限 |
| --- | --- |
| 游客 | 查看已开放的公共排行榜；不可读取用户余额、红包领取人明细或娱乐钱包 |
| 普通用户 | 使用已开放的签到、盲盒、转账、红包、娱乐大厅；查看自己的历史和允许公开的数据 |
| 管理员 | 配置开关和规则，管理奖池，查看资金业务列表，执行受控补偿/撤销，查看审计记录 |
| 系统任务 | 处理红包过期退款、盲盒奖励投递、失败重试、缓存失效和对账 |

所有管理操作必须经过管理员认证与合规守卫，并记录操作人、原因、时间、前后状态和关联流水。

## 6. 信息架构

### 6.1 用户端

侧栏新增一个一级入口“娱乐与活动”，避免将签到、转账、红包、排行榜和游戏逐项平铺。入口页采用本站工作台式布局，不做营销 Hero。

1. **活动首页**：今日签到、待处理盲盒、红包快捷领取、主余额、DG 余额、最近活动。
2. **签到中心**：普通签到、运气签到、连续天数、月历、今日结果、盲盒进度与历史。
3. **转账中心**：发起转账、转账明细、转账排行三个标签页。
4. **红包中心**：发红包/领红包分段控件；我发出的/我领取的标签页。
5. **排行榜**：余额、消费、签到、转账标签；消费和转账支持日/周/月周期。
6. **娱乐大厅**：DG 钱包、主余额兑换、游戏列表、奖池、最近游戏记录。

盲盒不单独占侧栏入口。签到触发后通过结果对话框展示，详细历史留在签到中心。

### 6.2 管理端

后台保留一个“功能开关”页签，内部按模块分区：

1. 入口与排行榜。
2. 签到与运气签到。
3. 签到盲盒与奖池。
4. 转账与红包。
5. 娱乐大厅与各游戏。
6. 兑换码、红包口令和邀请码格式。

每个模块使用“主开关 + 依赖提示 + 展开配置”的同一卡片结构。奖池、流水等复杂管理可通过卡片内“配置”按钮进入专页，但入口和业务开关不得再次复制到专页。

## 7. 功能需求

### 7.1 普通签到

- 每个用户按站点时区每日最多成功一次签到。
- 后台配置奖励最小值、最大值；服务端生成奖励并记录随机审计信息和规则版本。
- 成功后原子更新余额、签到记录、账务流水、连续天数和盲盒触发资格。
- 返回奖励、签到类型、连续天数、余额、盲盒投递状态。
- 重复请求返回当天既有结果，不重复奖励，不以数据库唯一冲突暴露 500。
- 支持最近 30 天月历、连续签到、累计签到和今日状态。
- 只开启运气签到时，签到入口和页面仍可访问。

### 7.2 运气签到

- 用户输入投注额，页面展示当前余额、可投范围、倍率范围和“可能亏损”提示。
- 提交前进行二次确认，确认后不得由前端重复提交。
- 新玩法统一定义为：`净余额变化 = 投注额 × (返还倍率 - 1)`。
- 返还倍率小于 1 表示亏损，等于 1 持平，大于 1 表示盈利。
- 用户行锁、余额校验、签到唯一性、余额变化、记录和账务流水必须在同一事务内完成。
- 并发转账、红包领取和运气签到不得导致负余额。
- 旧 lucky 历史仅用于展示和迁移，不重新结算。

### 7.3 签到盲盒

- 触发方式支持“连续签到每 N 天”和“累计签到每 N 次”。
- 奖品类型支持余额区间、并发数、订阅分组与天数、邀请码。
- 奖池项目包含名称、稀有度、奖励类型、最小/最大值、订阅分组、天数、权重、启用状态和软删除。
- 后台展示奖品总数、启用数、累计抽取数、总权重和归一化概率预览。
- 权重必须为正整数；稀有度与奖励类型使用枚举；订阅奖必须引用有效分组。
- 签到事务内创建唯一的“待发奖资格”；发奖 worker 可重试并记录 `pending/delivering/delivered/failed/compensated` 状态。
- 发奖必须有幂等键，签到成功后即使进程退出也能补发，不能吞掉错误或让用户失去机会。
- 抽中后使用本站 `BaseDialog` 展示奖品和实际到账状态；邀请码提供复制按钮。
- 管理端提供失败原因、重试和人工补偿入口，补偿同样写账务和审计。

### 7.4 余额转账

- 用户输入接收方 ID 后，服务端返回脱敏用户名/邮箱用于核对，并校验接收方存在且状态允许收款。
- 金额预校验返回手续费率、手续费、总扣款、日剩余额度和日剩余次数。
- 提交前二次确认接收方、到账金额、手续费和不可撤销说明。
- 支持单笔上下限、每日金额、每日次数、VIP 免手续费。
- 每日限额统一以 `gross_amount` 或 `amount` 为单一口径，PRD 决策采用**总扣款 gross amount**，并按站点时区计算自然日。
- 锁定发送方、检查限额、条件扣款、接收方入账、业务记录和双方账务流水必须在同一事务内。
- 历史支持转出/转入、状态、日期筛选、稳定排序和分页。
- 成功页展示流水号并刷新余额、统计和历史。
- “冻结”若仅是审计标记，文案改为“标记异常”；若需要冻结资金，必须使用 `frozen_balance` 和明确的解冻流程，不能只改历史状态。
- 撤销只允许符合条件的 direct 转账，并通过补偿流水完成；不得直接修改原流水或复用红包撤销逻辑。

### 7.5 红包

- 支持等额和拼手气两种分配方式。
- 创建表单包含总金额、份数、留言、类型和过期摘要，并展示手续费、最低单份和总扣款。
- 创建成功后展示格式化口令、复制和分享操作。
- 领取输入自动去首尾空格并按格式规则标准化大小写。
- 领取错误区分：不存在、已领取、已领完、已过期、自己领取自己的红包、功能关闭。
- 我的红包支持“我发出的/我领取的”、状态、剩余份数/金额、过期时间、分页和详情。
- 红包详情仅发送者、已领取用户和管理员可查看相应范围；其他用户只能通过口令读取脱敏领取前信息。
- 领取时锁定红包，扣减份数和余额、接收方入账、生成转账记录、claim 和账务流水必须同一事务。
- 后台定时任务使用 leader lock 扫描过期红包，原子退款且只退款一次；服务启动时执行补偿扫描。
- 领取与过期竞态只有一方成功，系统资金守恒。
- 红包领取的撤销必须更新 claim/红包状态并产生完整反向流水；首期默认不向管理员开放该能力。

### 7.6 排行榜

- 榜单类型：余额、消费、签到、转账。
- 消费榜和转账榜支持日、周、月；余额榜和签到榜为累计榜。
- 后台可独立控制总入口、各标签和是否包含管理员。
- 用户名按统一隐私规则脱敏；登录用户高亮“我的排名”。
- 前三名可使用站点图标和语义色增强，但不得使用 emoji 作为唯一信息。
- 支持稳定分页或加载更多；排序相同使用用户 ID 等稳定次序。
- 所有标签关闭时入口自动关闭，直链返回明确不可用状态。
- 查询错误必须显示错误与重试，不能伪装为空榜。
- 余额榜改为聚合查询，禁止逐用户查询签到次数；为常用周期和排序补索引/缓存。
- 消费口径为已成功计费的实际用户扣费，不含失败请求、退款和管理员手工调整。
- 转账榜默认按成功 direct 转账的到账金额统计，不含红包、批量发放、撤销和手续费。

### 7.7 娱乐大厅

娱乐大厅以 `langhun/sub2api` 的钱包隔离和游戏服务分层为参考，不直接照搬当前主线，因为其当前树只保留部分老虎机骨架，历史上的 train、简化 Texas 和双色球链路已被移除或不完整。

#### 7.7.1 钱包与兑换

- 主余额与 DG 娱乐余额按 1:1 双向兑换。
- DG 钱包必须独立存储，游戏下注不得直接修改主余额。
- 每次兑换同时写主余额账务和 DG 钱包流水，使用同一个业务引用和幂等键。
- 主余额更新必须走统一余额域服务，触发服务端缓存失效，不允许绕过账务直接 `UPDATE users.balance`。
- 后台可配置单次兑换上下限、每日兑换上限、是否允许 DG 转回主余额。
- 支持按用户禁用娱乐功能；只有全站总开关不足以处理风控账号。
- 大厅关闭后不允许新兑换和新下注，但保留查询与管理员清算能力。

#### 7.7.2 奖池与游戏

- 首期 P0 游戏仅开放三轴老虎机，先完成稳定的钱包、奖池、账务、幂等和风控底座。
- P1 候选玩法为 train、简化 Texas、双色球；每个玩法必须独立评审规则、公平性、结算状态机和合规性后才能启用。
- 游戏配置包含启用状态、最小/最大投注、赔率表/规则版本、单用户频率限制和每日亏损上限。
- 每个已审批规则版本必须定义目标 RTP、波动率和统计容差；后台展示理论 RTP，但不能绕过审批直接修改概率。
- 公共奖池记录当前余额、启用状态；每次下注入池和派彩出池均写不可变奖池流水。
- 派彩金额不得超过奖池可用余额；若采用封顶派彩，结果必须在下注前规则中明确，不能临时改变用户已确认的赔率。
- 每一局记录用户、游戏类型、投注、派彩、净额、规则版本、随机审计数据、结果、状态和幂等键。
- 服务端生成结果，前端动画只呈现已结算结果，不能参与随机决定。
- 随机数使用 `crypto/rand` 或可审计的安全随机方案，不使用 `math/rand` 处理真实余额玩法。
- 管理端提供奖池余额、收支、RTP、局数、活跃用户、异常局和对账差异，不提供直接篡改结果能力。
- 参考实现当前三轴权重的理论 RTP 约为 15.69%，远低于其历史版本约 95.3%，因此不得沿用现参数。上线前至少完成百万局概率仿真和奖池枯竭压力测试。

## 8. 统一设置矩阵

| 模块 | 主开关 | 子开关/展示 | 规则 |
| --- | --- | --- | --- |
| 签到 | 签到入口 | 普通签到、运气签到 | 普通奖励区间、投注区间、返还倍率区间、站点时区 |
| 盲盒 | 盲盒奖励 | 进度提示、历史展示 | 连续/累计触发、间隔、奖池、失败重试 |
| 转账 | 余额转账 | 转账排行、VIP 免手续费 | 费率、单笔上下限、每日总扣款/次数 |
| 红包 | 红包入口 | 等额、拼手气、领取记录 | 最大份数、期限、最低单份、费率 |
| 排行榜 | 排行榜入口 | 余额、消费、签到、转账、包含管理员 | 默认标签、周期、分页大小、脱敏方式 |
| 娱乐大厅 | 大厅入口 | DG 兑换、各游戏入口 | 兑换限制、投注限制、赔率版本、风控 |
| 代码格式 | 格式引擎 | 余额码、并发码、订阅码、红包口令、邀请码 | 前缀、字符集、分隔符、组长、组数 |

依赖规则：

- 签到入口开启条件为普通签到或运气签到至少一个开启。
- 盲盒开启时必须至少一种签到方式开启且至少一个有效奖品存在。
- 转账关闭时转账排行同步关闭。
- 排行榜开启时至少一个标签开启。
- 红包入口可独立关闭，但底层复用统一余额账务能力。
- 娱乐大厅入口开启时至少一个游戏或 DG 兑换能力可用。
- 被单独禁用娱乐功能的用户即使全站开关开启，也无法兑换或下注。
- 配置保存后，管理设置、公开设置、SSR 注入、前端 store、侧栏、路由守卫、Handler 和 Service 必须同轮生效。

开关采用三层防护：展示层隐藏入口，Handler 层拒绝直链/API，Service 层在执行前再次校验。关闭返回稳定业务码，不依赖前端阻止。

## 9. 兑换码与口令格式引擎

余额兑换码、并发兑换码、订阅兑换码、红包口令和邀请码共用一个生成器及配置组件，但每类独立配置：

- 前缀。
- 字符集：大写字母、数字、字母数字、十六进制。
- 分隔符：无、短横线、下划线或自定义单字符。
- 每组字符数。
- 组数。
- 实时示例、总长度和可用组合空间提示。
- 唯一索引冲突后的安全重试次数。

服务端必须校验字符集、长度、分隔符和组合空间，使用安全随机源。格式变化只影响新生成的代码，历史代码必须继续可兑换。红包口令不能通过 public settings 暴露不必要的安全参数。

## 10. 数据模型

### 10.1 现有业务表保留并强化

| 表 | 用途 | 关键约束 |
| --- | --- | --- |
| `checkins` | 每日签到事实 | 唯一 `(user_id, checkin_date)`；类型枚举；金额精度 |
| `checkin_prize_items` | 盲盒奖池 | 正权重；类型/稀有度枚举；软删除 |
| `checkin_blindbox_records` | 抽取与奖品快照 | 用户索引；奖品引用可空 FK；保存规则版本 |
| `balance_transfers` | 转账业务状态 | 类型/状态枚举；发送方/接收方/时间索引 |
| `balance_redpackets` | 红包状态与余量 | 唯一口令；非负 CHECK；状态/过期索引 |
| `balance_redpacket_claims` | 红包领取 | 唯一 `(redpacket_id, user_id)`；transfer 可空 FK |

### 10.2 新增通用账务与投递表

`balance_ledger`

- `id`、`user_id`、`event_type`、`reference_type`、`reference_id`。
- `idempotency_key`，对业务范围唯一。
- `delta`、`balance_before`、`balance_after`，均为 `DECIMAL(20,8)`。
- `metadata JSONB`、`created_at`。
- 流水不可 UPDATE/DELETE；纠错新增补偿流水。

`reward_deliveries`

- `source_type/source_id/user_id/reward_type`。
- 奖励快照、`status`、`attempts`、`last_error`、`next_retry_at`。
- 唯一幂等键、创建/完成时间。

通用账务解决当前所有正向余额变化被误计为 `total_recharged` 的问题。`total_recharged` 只由真实支付充值更新，签到、盲盒、转账、红包、游戏和后台补偿不得计入充值。

### 10.3 娱乐大厅专用表

| 表 | 用途 |
| --- | --- |
| `game_hall_wallets` | 用户 DG 当前余额 |
| `game_hall_wallet_transactions` | DG 兑换、投注、派彩流水 |
| `game_hall_jackpots` | 奖池当前余额和状态 |

## 12. 迁移方案

### 12.1 旧签到数据

当前移植迁移只创建 `checkins`，没有迁移真实旧表 `checkin_records`，现有回归测试也未覆盖该路径。上线前新增 forward-only 幂等迁移：

1. 检测旧表和字段是否存在，迁移前生成行数、用户数、奖励合计和非法日期报告。
2. `normal -> normal`；`lucky -> luck`。
3. 普通签到 `bet_amount=0,multiplier=0`。
4. 旧 lucky 记录按旧语义迁移为历史快照：`bet_amount=balance_before`，`multiplier=1+random_value`，但不重新入账。
5. `checked_at -> created_at`，字符串日期安全转换为站点日期；非法行进入迁移报告并阻止静默上线。
6. 使用 `(user_id, checkin_date)` 冲突策略保证重跑安全。
7. 用窗口函数按日期重算 `streak_days`。
8. 新设置不存在时才映射旧键；管理员已保存的新配置优先。
9. 保留旧表为只读归档至少一个版本，不在同一迁移删除。

迁移验收：0 丢行、0 重复、用户数和奖励合计一致、旧开关不被覆盖，重复执行结果不变。

### 12.2 娱乐数据

- 检测旧 `game_wallets/game_wallet_transactions/game_jackpots/game_jackpot_transactions`。
- 有流水的账户按流水和快照核对后迁入专用 `game_hall_*` 表。
- 只有余额快照、没有流水的账户不得简单覆盖；使用一次性基线流水记录来源。
- 每个用户和奖池生成迁移差异报告，差异非零时停止开放大厅。
- 迁移不直接修改旧表，切换后只读保留一个版本。

### 12.3 上线顺序

1. 上线表、账务、迁移与双读核对，所有新功能保持关闭。
2. 完成后台设置和只读页面。
3. 小范围开启签到与排行榜。
4. 开启转账和红包，并监控对账、限额和过期任务。
5. 最后开启 DG 兑换和老虎机；其他游戏另行评审。

## 13. 安全、风控与一致性

- 所有资金写入在数据库事务内完成，使用行锁或条件更新保证余额不为负。
- 每个业务动作必须具备幂等键、业务记录和账务流水。
- 红包口令、兑换码、邀请码和游戏随机数使用 `crypto/rand`。
- 管理端配置校验 `min <= max`、费率范围、finite 数值、正权重、正间隔和合法枚举。
- 对签到、转账、抢红包、兑换和游戏设置用户/IP 速率限制与异常告警。
- 可配置单日转账、红包、娱乐兑换、投注和亏损上限。
- 红包详情、排行榜和转账核验按最小必要原则脱敏，不返回无关用户 ID 或邮箱。
- 缓存只作为读取加速，不作为余额真相；余额变更后必须失效相关认证、账单和公开设置缓存。
- 每日执行资金守恒对账：主余额、DG 钱包、奖池、手续费、外部发行和补偿均可解释。

- 真实 `checkin_records` 快照迁移后 0 丢行、0 重复、奖励合计一致。
