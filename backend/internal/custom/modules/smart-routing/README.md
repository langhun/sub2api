# 智能路由故障隔离修复（2026-09-19）

本次修复针对用户回退版本后确认的故障：少数坏上游网站导致整组被隔离，整组恢复租约占用又把健康网站挡在调度之外；池模式持续调用余额不足的上游；错误日志混用了失败网站与最终成功分组。

这里的 `account` 数据库记录代表一个上游网站/渠道，不代表该网站内部池中的成员账号。池内成员由上游网站自行选择，本系统无法观察其身份或健康状态。

## 两种上游形态

智能路由同时支持外部网站池和自有账号池，二者不能混为一个健康单元：

- **外部网站池**：一条 `account` 记录对应一个网站入口，并开启 `pool_mode=true`。网站内部成员失败只触发该网站入口的请求内重试；只有网站池重试耗尽，才隔离这条 `account`。
- **自有账号池**：将每个可直接调用的账号作为独立 `account` 加入同一分组。每个账号单独参与速度、成功率、容量和健康判断；一个账号失败不会隔离同池其他账号。
- 如果自有聚合网关本身也会在内部换号，可将该网关入口配置为 `pool_mode=true`，系统会把它当作外部网站池处理，而不会假设能看到内部成员。

因此，`pool_mode` 是单条上游入口的重试语义，不是分组级开关，也不会让同一分组内的普通账号共享冷却、粘性或失败计数。

## 设计依据

研究了以下项目的官方文档或代码，再按当前 Overlay 和网关接口实现，没有引入第二套路由引擎：

- [Envoy Outlier Detection](https://github.com/envoyproxy/envoy/blob/main/docs/root/intro/arch_overview/upstream/outlier.rst)：按实际 upstream host 隔离，区分请求与上游故障，恢复失败逐步延长隔离。
- [sony/gobreaker](https://github.com/sony/gobreaker)：半开状态限制探测并发，取消等排除事件不计入失败。
- [LiteLLM cooldown handlers](https://github.com/BerriAI/litellm/blob/main/litellm/router_utils/cooldown_handlers.py)：对实际 deployment 记故障，不将编排或客户端原因盲目归因到模型服务。

这些原则适合当前多上游网站分组结构。整组熔断无法区分同组好坏网站，不能继续作为默认故障隔离单元。

## 请求行为

1. 按现有权限、平台、订阅类型、模型与容量要求生成候选池。
2. 过滤冷却中或已有恢复探测在途的网站；同组其他健康网站继续参与策略评分和调度。
3. 真正转发前再次原子检查网站健康状态，阻止评分到转发之间的并发竞态。
4. 非池模式故障立即发布网站隔离状态；池模式先在同一网站内重试，由上游自行轮换池成员。
5. 默认 `pool_mode_retry_count=3`，即初次尝试失败后最多再请求同一网站 3 次。中间失败只进入统计，不触发网站冷却；全部耗尽或已产生输出无法继续重试时，才记录网站级失败。
6. 同站重试使用一次性请求内锁定，速度评分、粘性和负载排序不能把尚未耗尽的池重试抢到另一网站；下一次选号完成即清除，不形成会话粘性。
7. 同一网站耗尽后先尝试当前分组其余网站，再按现有预算切换候选分组。全部不可用时记录原因并返回错误。
8. 已产生输出时不跨组重放；请求取消、用户参数错误和明确请求级故障不处罚网站。
9. 智能路由请求最多启动 12 次上游尝试，且墙钟预算默认为 30 秒；预算只对已激活的智能路由生效，普通单分组请求保持原有重试行为。
10. 余额/额度耗尽、明确模型不支持和“所有账号均被限流”等确定性错误不再消耗隐藏池成员重试；普通 429/503 仍遵守上游显式池重试配置。

速度策略仍使用既有分组评分及模型/端点/流式维度的账号延迟指标，不把粘性账号强制前置；健康过滤先于软评分。速度优先不等于每个请求都保证最快，历史样本、容量和连续性要求仍会影响选择。显式的价格/速度/成功率/自定义策略不再触发冷候选探索；仅自动策略保留最多 1% 的冷启动探索，兼容旧配置中的 5% 字段但运行时不会按 5% 放量。

## 账号状态与恢复

| 项目 | 行为 |
| --- | --- |
| 隔离维度 | 上游网站记录（account ID）+ requested model + endpoint + stream；同一网站跨组共享故障 |
| 池模式中间失败 | 只记录尝试指标，不跨请求累计失败次数，不立即隔离网站 |
| 池模式最终失败 | Handler 确认同网站重试预算耗尽后才进入网站冷却 |
| 普通可归责上游故障 | 首次冷却 30 秒 |
| 可归责 401/402/403 | 首次冷却 5 分钟，避免反复调用无效凭据/额度耗尽线路 |
| 恢复再次失败 | 按失败次数指数退避，上限 15 分钟 |
| 冷却期间旧在途失败 | 不反复延长正在生效的冷却 |
| 半开探测 | 每上游网站一个 Redis 租约，正常网站无需探测租约 |
| 租约期限 | 硬 TTL 5 分钟；结束/取消正常及时释放，异常退出靠 TTL 回收 |
| 恢复正常 | 连续两次有效探测成功；普通旧请求的迟到成功不能清除冷却 |
| 防止迟到请求污染 | 探测 token 校验；旧 token 不能解除新租约或确认新状态恢复 |
| Redis 失联 | 有界进程内降级；健康账号继续服务，故障账号本地冷却 |

Redis 故障期间无法保证跨进程只有一个探测，各节点仅保证本地限制。Redis 探测中途断开后的失败也进入本地冷却；没有有效租约的成功不会直接确认恢复。进程内状态最多 4096 项，健康状态保留上限 24 小时；容量耗尽时属于保护能力降级，不承诺无限网站/模型组合都保留状态。

新 Redis 命名空间为 `custom:route:account:v2:{hash}`。旧 `custom:route:health:*` 整组 recovering 标记不再消费，无需清理生产 Redis，不修改账号管理状态，也不恢复 30 分钟跨组粘性。单分组请求不进入新增健康准入逻辑。

## 可追溯性

- 选择账号时保存实际分组；每条上游失败和流式错误都携带发生当时的分组快照。
- 错误日志优先使用失败事件的 group/account 配对。成功用量继续由原有计费链路记录，不拿最终成功组覆盖失败事件。
- 无路由时异步写 `no_available_route`，`selected_group_id=NULL`，附候选原因、账号排除原因、尝试次数、切组次数和连续性限制。
- 每个智能路由请求异步写一条 `custom_route_outcomes` 终态记录，保存最终成功/失败、实际分组/网站、总尝试数、切组数、耗时、首 token 和最终错误码；中间失败后恢复不会被当成客户最终失败。
- 无路由审计最多 64 个在途写入、单次 2 秒上限，满载记录告警；审计失败不会阻塞推理。它是尽力记录，不能承诺数据库故障下零丢失。
